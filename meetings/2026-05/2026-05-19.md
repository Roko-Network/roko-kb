# Development Meeting Summary

**Date:** May 19, 2026

---

## Explorer V2 Progress

The new version of the block explorer (V2) is nearing readiness, with work split across two sides. On the node side, improved indexers were added so the explorer can expose substrate-level information — blocks, extrinsic calls, constants, available parameters, and pallets — alongside EVM data. While Polkadot.js can still fetch this information through normal paths, having archive-mode nodes expose indexed data directly simplifies running a full explorer. The nodes were updated and the new version is running on the Raspberry Pi hardware. On the front end, new components are in testing that provide developer-level access to the chain, such as creating extrinsics and carrying parameter information — functionality previously available through Polkadot.js, now merged into the Blockscout-based explorer.

## Unified EVM and Substrate Data

The explorer's database schema was updated to handle both EVM and substrate blocks, with time information living at both the substrate and EVM levels. An open design question is how to present all of this without overwhelming users: those interacting with the chain purely as an EVM chain should not be forced to engage with substrate internals, yet many of the more technical and developer-oriented features live on the substrate side, and the explorer should help users track transactions, surface issues, and debug.

## Chain Update Path

The substrate runtime upgrade path was incidentally validated. Because substrate chains can ship runtime logic as a Wasm image that nodes execute without a full binary update, most chain updates do not require the node binary to be replaced — though specific features such as new indexers do require the updated binary. During this work the Raspberry Pi hardware upgraded automatically and cleanly via the standard substrate update mechanism.

## Reward Framework Document Review

The team reviewed a circulated positioning document analyzing Roko's value proposition, prepared using an external value-framework methodology. It was characterized as a mature, high-level pitch document intended for interested parties, derived from the project's current repositories and documentation rather than older aspirational material. The team discussed evolving parts of it into a formal white paper. It was noted that the reward-system and tokenomics content in the document reflects the current state rather than the desired end state, and that those sections will need adjustment as the framework matures.

## Timing Hardware Status

Setup of the new validator with the improved timing hardware is in progress but currently blocked on networking configuration following a switch change. The hardware appears to have been flashed correctly with the custom image, but the node's IP address could not yet be resolved while the router operates in bridge mode. The team offered support and expects the node online within a few days.

## Open Reward Decisions

Several reward decisions remain unresolved and were flagged as the priority for an upcoming dedicated session: which path to keep for rewards denominated in Power Roko versus Roko, and how to handle the conversion from the current Roko token to the native currency of the testnet and later mainnet (whether at a one-to-one ratio or otherwise). The team agreed to dedicate the next call to rewards, with a presentation of the current reward state recorded and a discussion of the possibilities, compiled into a document to move the decision forward.

## Ecosystem Context

A portion of the meeting covered an adjacent open-source evaluation effort and broader edge-AI strategy not specific to Roko. The most relevant connection for Roko is the shared "get the general public in first, surface crypto only where wanted" funnel philosophy: consumer-facing apps and services are positioned without crypto framing, with crypto interfaces available for users who want them, and Roko-related offerings layered in over time. A unified evaluation harness for comparing agentic configurations and an in-browser encrypted-client pattern (modeled on privacy-first service architectures) were discussed as future areas of collaboration.

- Hold a dedicated session on rewards: present the current state, discuss options, and compile a decision document.
