# Strategy Meeting Summary

**Date:** February 17, 2026

---

## Time Mesh as a Blockchain Foundation

The discussion opened on how closely a decentralized time mesh already resembles a blockchain. The chain developer noted that established time-mesh networks have already survived manipulation attacks: reputation for bad time providers drops so quickly that a network can shrink dramatically and still maintain correct time, making time manipulation prohibitively resource-intensive — comparable to attacking proof-of-stake or proof-of-work systems. The mesh is decentralized, distributed, attack-resilient, authority-free, and can assure correct time without certificates, which together represent most of the defining properties of a blockchain. The view expressed was that the project now combines the timekeeping community's work on time with the blockchain world's needs, positioning it as a genuinely time-first chain.

## Layer-1 Versus Parachain and Layer-2 Options

Several structural options were weighed. A parachain path was raised as technically possible — retaining the time-mesh capability while integrating with another ecosystem — but seen as more oriented toward corporate/enterprise use and as limiting access to DeFi. A layer-2 framing was also explored: because the time-mesh technology provides a genuinely novel capability (providing accurate time to another ecosystem with deep integration rather than a mere bridge), it could be seen as a deserving layer-2 in the spirit of recent commentary on what legitimate layer-2s require. A further model discussed was a white-label / "legitimacy layer" approach, where other projects could build on the chain's tooling and time guarantees. The team's stated preference was to pursue layer-1, while remaining open to a parachain or layer-2 if investor interest or other factors warranted it. DeFi was framed as an eventual goal contingent on multiple conditions aligning.

## Public Repository and Announcement Timing

The team assessed readiness to open a public-facing repository. The main blocker over recent months had been the shifting code base and uncertainty about what contributors would be asked to commit to; with the architecture now stabilizing, the expectation is that the next meeting can confirm the chosen design, with subsequent changes treated as point releases. The proposed sequencing is to validate via a testnet running real time hardware, share the testnet publicly once a few nodes are running, open the code base roughly a week before announcements, and follow with the main announcements a few days later. Documentation, payment mechanics, and the economic numbers were identified as the items still to be finalized so they can be communicated clearly. One participant volunteered to draft a one-page timeline so the team can align on roles and responsibilities.

## Internal Tooling and Automation

The team discussed building an ecosystem of automation bots to manage contributions — reviewing pull requests, processing issues, and self-cycling on improvements — and the idea of tooling to identify and tier the most valuable external contributions. A centralized, shared memory system was proposed as the coordination point for multiple agents, to be hosted on the team's high-performance server, including a possible internal "back office" endpoint where team members could query current project knowledge, pitch material, and vision. Authentication for these services is largely in place, with plans to issue team logins (including MFA) that grant access to the shared memory and its interfaces. A self-improvement feedback concept was also raised, in which approved agents would autonomously send issues and improvement suggestions rather than waiting to be prompted.

## Time Hardware and Testnet Configuration

A substantial portion of the meeting covered the physical time infrastructure. The team inventoried its available time cards and grandmaster appliances and discussed how to configure them. For the precision targeted, dedicated hardware is required: the grandmaster appliances are kept air-gapped as shipped, distributing their time signal over a PPS line to a receiver card, with the validator running the PTP-squared application on a separate machine. For home, edge, and development/test scenarios, running PTP-squared directly on small boards (such as a Raspberry Pi) is an acceptable configuration, with the trade-off of reduced precision; analog PPS is the recommended production configuration to avoid wasting validator cycles. The team also discussed connecting to the partner's existing public time network as an option for testing, while preferring initially to run their own small network to build operational knowledge. Sourcing reliable PPS cables and receiver cards — noting that cable termination is finicky and a good supplier is still needed — was flagged as a practical follow-up. A note was made that GPS antennas are still awaited for the clock network, which does not block testnet work but is wanted ahead of mainnet.
