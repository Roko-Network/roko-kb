# Development Meeting Summary

**Date:** February 10, 2026

---

## Time-Mesh Integration into the Chain

The chain developer presented a major architectural shift: embedding the time-mesh logic directly inside the validator nodes so that the network converges on accurate time as a first-class function rather than relying on an external time source. The approach builds on earlier testnet work that validated transaction inclusion enforcement, and extends it by running a PTP-squared time-mesh engine within each substrate node. Every validator now participates in the mesh as a time provider, while light nodes act as relayers. The result, in theory, is a network that is a time mesh in its own right and also happens to produce blocks and process transactions.

## New Pallet Architecture

Two new pallets were introduced: a TimeSync pallet implementing the PTP-squared algorithm and the time-mesh engine, plus a bridge pallet that carries time-mesh information onto the chain. A modified block-finalization layer uses the time-sync inherents to validate accurate time, and block time is set to the mesh-derived median time, with blocks rejected if the time is incorrect. The temporal-transaction and court layers continue to function as before, but the previous time RPC and its centralized entity are no longer required, since any validator can now provide valid time attestation. Legacy transaction support remains in place.

## Anti-Manipulation and Reputation

The design includes mechanisms to detect validators that copy time rather than genuinely provide it: roughly every hundred blocks a validator is sampled and its reported time, drift, and related values are compared against the mesh consensus, flagging nodes whose values merely mirror another node's. A reputation system scored from zero to one weights each validator's contribution to the median time and influences block-production selection and rewards. The intended effect is that validators providing poor time lose reputation and rewards, while reliable providers earn more, so that even a substantial fraction of bad actors does not corrupt network time. Proof-of-stake is retained primarily for Sybil resistance and could be scaled down later, given that the hardware investment to become a validator itself functions as a form of stake.

## Status and Validation Plan

The team noted that the architecture and code exist with extensive tests, but the integrated network has not yet been deployed or validated end to end — it remains explicitly experimental. Remaining work discussed includes moving the courts off the beacons to a deeper layer (potentially relocating Merkle-root sharing for enforcement to a gossip-level protocol) and resolving a block-timestamp issue. The plan is to stand up a new experimental testnet alongside the existing one so the new version can be evaluated without committing to it. This testnet does not require dedicated time hardware; a later validation milestone would run a full time mesh with GNSS-synced hardware.

## Go-to-Market and Product Direction

The group discussed positioning the network around its time-mesh capability, which offers a narrative accessible even to audiences unfamiliar with blockchain — framing the project as a decentralized timekeeping network with blockchain capabilities layered on top. Participants emphasized prioritizing a public-facing testnet and concrete demonstration applications over abstract block-explorer views, on the view that a visible, working network would build credibility with prospective users and investors. Several future product tracks were raised for evaluation, including a carefully staged path toward DeFi, a data marketplace, and a lower-compute-cost hosting/deployment offering. The team agreed to coalesce around a near-term timeline and a prioritized list of deliverables, targeting production-ready applications on a public testnet ahead of a later mainnet milestone.
