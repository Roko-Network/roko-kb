# Development Meeting Summary

**Date:** June 4, 2026

---

## Time Mesh Consensus Refactor

The team completed a significant rework of the time mesh consensus and deployed it to testnet. The previous design weighted route distance between validators heavily, which penalized geographically distant nodes — a cluster of free validators running on Amazon behaved like a local network with very low route distance, while a Raspberry Pi node sat far enough away to expose how hard it would be for globally distributed clusters to earn good scores. Because a blockchain is inherently distributed worldwide, the consensus was reworked to reward time quality over route distance, decoupling the precision a validator produces from the time it takes to propagate that signal to peers.

Loosening the route-distance requirement raised the overall mesh time precision to roughly 200 milliseconds, which the team considers still exceptionally strong for a blockchain. Validators now timestamp transactions using their own GNSS-trained time hardware, and the protocol can still detect and flush irregularities within a fifteen-millisecond tolerance. The change was described as a heavy rewire of what the time mesh expects from participants, the result of two to three weeks of investigation. It is now live on testnet and undergoing extensive adversarial testing.

## Optimistic Validation and the Cheating Window

The new model shifts toward an optimistic approach: rather than relying on a converged mesh time for blocks, the network trusts each validator's local time when it stamps its own block and then works to prove and slash dishonest behavior. The mesh time is retained primarily to discipline newcomers and help them start on solid footing. A validator can still cheat timestamping within a roughly fifteen-millisecond window, but doing so is detectable and results in slashing. The team noted this is a small window relative to a two-second block time, and that as more validators join, the tolerance could narrow — though that is not guaranteed, since propagation delay between globally distributed validators is a physical limit.

The discussion drew an analogy to standard GNSS time protocols, which similarly accept a propagation tolerance and use regular challenges to force time providers to improve quality and shrink the cheating window. The team plans to revisit whether the tolerance can be tightened once the network reaches around twenty nodes and observable patterns emerge.

## Validator Hardware Implications

The refactor raised the bar for validator hardware. Because the mesh now treats validators by time quality, the Amazon-hosted nodes — which lack dedicated time hardware — are now considered disciplined rather than authoritative and are effectively weaker than the GNSS-trained Pi node. The team identified a need to import more time-grade hardware. With only four validators currently online, certain attack scenarios (including single-validator attacks) cannot yet be fully tested, but every test that can be run is being executed as part of the standard validation routine for major development stages. The team emphasized the change is purely technical and does not alter hardware requirements, chain behavior, or the time-quality guarantees from a product or marketing standpoint.

## Smart Contract Tooling and Verification

A community developer reported forking the Roko GitHub and deploying a range of experimental smart contracts to testnet, building subnet-style demos (including a prediction-market concept) with working front ends. The team confirmed there is no dedicated on-chain indexing for smart contracts; contracts are deployed and detected through the standard EVM transaction pathways, while the block explorer maintains awareness of deployed contracts and can accept verified source code. On reverse-engineering, the team noted that unverified bytecode should generally be treated as effectively open-source given modern decompilation and AI tooling, especially for simpler contracts, though specific obfuscation techniques exist. The team recommended verifying deployed contracts so their behavior is visible, and suggested publishing example contracts to a repository to demonstrate what can be built on Roko.

## Parallel Consensus Experiment

The community developer asked about a separate consensus approach being prototyped that measures the phase noise of a validator's clock as an additional probe, noting the protocol's existing rate limits on the number of probes a validator can exchange in a given window. The plan discussed was to prepare a short write-up and pseudocode, then use the developer's forked environment to run deeper testing against the live testnet before any formal push.

## Next Steps

- Continue adversarial testing of the reworked consensus on testnet across attack vectors before promoting the change.
- Acquire additional time-grade validator hardware to replace reliance on the Amazon-hosted nodes.
- Publish example smart contracts and front-end demos to a Roko repository as reference material.
- Verify deployed testnet contracts through the explorer so their behavior is auditable.
- Prepare a write-up and pseudocode for the phase-noise probe and test it against the forked testnet environment.
