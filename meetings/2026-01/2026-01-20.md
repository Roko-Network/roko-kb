# Development Meeting Summary

**Date:** January 20, 2026

## Deployment Pipeline

The team is standardizing node deployment around Docker, with the intent to support deployment across all three platforms and to provide compile-from-source instructions as well. The Docker image — which contains the prebuilt Roko Network node binary and accepts the binary's normal arguments for versatility — needs to be made public so that the validator-creation flow on the Roko admin dashboard can pull and run it. The intended user experience is a single button on the dashboard that generates a script; the user copies and runs that script, which pulls the Docker image, runs the node, and exposes local dashboards for debugging (showing cached beacons from validators, block production, and similar diagnostics).

## Testnet and Genesis Fixes

Several issues were worked through during the week. Beacon sync problems on the substrate side required repeated rebuilds, though newer Rust caching tools have made builds smaller and faster. A node went out of sync due to an epoch-randomness issue that caused other nodes to reject its beacons, which required stabilizing the randomness key used for beacons. A genesis-configuration problem was also found: the testnet had a hard-coded limit of five nodes (a substrate testnet-specific setting that does not exist on mainnet), which prevented adding more validators. The current process is to deploy a clean testnet, walk through the validator-creation flow, run the generated script, and fix issues iteratively until it works without manual changes.

## AI-Assisted Development Workflow

A substantial discussion covered tooling and AI-assisted development. The team compared coding setups and plan economics across several agentic tools and noted that AI is strong at generating dashboards but weak at debugging chain state, where it requires significant input and nudging. The persistent-loop approach (running an agent that keeps grinding on a problem) was discussed as effective but token-intensive.

The internally developed AIWG framework was presented as an approach to this problem. The premise is that letting an agent freely figure out architecture, stack, and design decisions leads to thrashing and hallucination; AIWG front-loads planning into a structured, linked set of documents based on project-management methodology, providing guardrails that enable longer agent runs and more reliable task completion. The framework follows a waterfall-style documentation methodology — an interactive intake process that adapts to the user's technical level, then progressively detailed "flows" with gate checks that validate enough documentation exists before proceeding, down to near-pseudocode before a construction phase. Once the document base exists, code revisions drift less because the model can refer back to a defined reference. The team agreed to try running the testnet work through the AIWG intake process.

## Build Automation and Future Direction

A future direction discussed was moving toward an issue/ticket-driven workflow where contributors can file tickets and work with a coding agent in a sandboxed VM, reducing direct CLI involvement. The need to set up a safe, isolated agentic VM environment for this was noted. Separately, the team mentioned in-progress work on a memory system (a Docker-packaged service running an embedding server with multiple search indexes, exposed over REST with an MCP server and a UI) that could be tested internally.

## Fee System and Time-Security Follow-Up

Two action items were emphasized at the close. First, the team asked for input on the temporal transaction fee system, building on the previously shared document, so that an implementation plan and investor-facing description of how fees work can be validated. Second, following the recent Timebeat call, the team wants to look deeper into integrating with the security of the Timebeat time devices and giving another attempt at building a consensus around proof of time. The realistic near-term path discussed was to assess whether the default substrate consensus layer could be modified or replaced just enough to use the cryptographic security of time networks — while being careful not to over-commit, given current time and funding constraints, and treating the blockchain-way approach as the working baseline.
