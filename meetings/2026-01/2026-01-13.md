# Development Meeting Summary

**Date:** January 13, 2026

---

## Validator Onboarding

The team reported that the validator deployment flow now works end-to-end. The script generated by the Roko admin interface — which a user runs after creating a validator — was fixed so that it correctly injects the validator key in the right location and handles the per-transaction temporal signing the network now requires. A key issue was resolved around EVM versus SS58 key formats, where the wrong key type had previously been injected. The node now runs under Docker, produces beacons, and the prebuilt image is published to the Roko Network packages on GitHub so anyone can pull and run it. Docker clock handling was flagged as something to keep an eye on, since the clock is passed through from the host OS rather than managed by the container.

## Reward Tracking and Gamification

Development is underway on a rewards-tracking application intended to reward participants in testnet testing. The app uses a modular system that parses configurable on-chain events to detect activity such as transactions, staking, voting, and block production. A proposal was discussed to gamify participation through tester levels — for example, completing ten transactions, staking, acquiring Power Roko, participating in a vote, and running a validator as progressively higher tiers. Levels for validator operators could scale with blocks produced. The team noted this approach would simplify reward distribution (rewarding by level reached rather than computing per-activity payouts) and could tie into a community badge or bot system across Discord and Telegram. It was noted that any community points should remain clearly non-monetary and decoupled from token value for compliance reasons.

## Mempool Hash Consensus

Work is in progress on a mechanism to prevent block producers from skipping or reordering temporal transactions. The proposed approach embeds a hash of the beacon producer's view of the mempool into the beacon data. A block producer would then be required to select beacons whose mempool hash matches its own, providing evidence that transactions were included and executed in order. This was identified as something that should be validated before finalizing the fee system.

## Transaction Fees and Tokenomics

A significant portion of the meeting was devoted to the open problem of transaction fees under time-based ordering. Because temporal transactions are ordered by time rather than by fee competition, the usual market mechanism that lets fees converge on a price no longer applies — a transaction must execute within its time frame regardless of fee. A simple fixed fee in Roko was considered but rejected as the sole solution, since it cannot automatically adjust to Roko's market price the way gas markets do on chains like Ethereum.

Several directions were explored. One idea was to gate temporal transactions behind a market mechanism where participants pre-purchase temporal transactions in packages — analogous to purchasing API calls — with validators minting these as they produce blocks and reselling them on an open market. Another idea was to let fees buy precision, where cheaper transactions receive a wider time window and more expensive transactions are narrowed toward sub-second or sub-100-millisecond accuracy. The team agreed to investigate an on-chain open market for temporal transactions and to verify the mempool-hash mechanism first, with a few days of focused work planned to define the fee approach.

## Funding and Prioritization

The team discussed the tension between development pace and treasury runway, noting that articulating tokenomics for investor materials depends on first resolving how the network charges for transactions. At a high level, Power Roko is positioned as the governance token while additional utility mechanisms remain to be defined. The group weighed whether adding a developer would accelerate the fee work and concluded it likely would not speed things up materially; instead, the existing developer agreed to reprioritize toward solving the fees problem. A recurring theme was the value of reaching a clear, demonstrable core use case — particularly MEV protection as a consequence of time-ordered transactions — as a near-term proof of concept and selling point for both Web3 and traditional-finance audiences.

## Next Steps

- Bring the validator onboarding flow to a fully repeatable state (pull image, run script, join chain) under testnet.
- Verify the mempool-hash consensus mechanism works as intended.
- Dedicate focused time to defining the temporal transaction fee model, including the pre-purchased-transaction market concept.
- Continue the reward tracker while prioritizing the fee work.
- Explore MEV protection as a demonstrable use case for investor and partner conversations.
