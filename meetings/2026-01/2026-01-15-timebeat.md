# Partner Call Summary

**Date:** January 15, 2026

---

## Purpose

This was a presentation and consultation call with Timebeat, the timing-hardware partner. The team walked Timebeat through the Roko Network's blockchain architecture and current functionality, then sought input on how the network's time-attestation needs could leverage Timebeat's time-synchronization technology.

## Roko Architecture Overview

The team explained that Roko treats time as a first-class, time-attested feature. On standard blockchains, the block timestamp is set by the miner within a tolerance window, which is widely known to be untrustworthy and is exploited for value extraction — for example, manipulating when a vesting period ends, or front-running and sandwich attacks. Roko's goal is to remove time-setting from the block producer and instead establish time through consensus. Two pipelines were described: validators continuously gossip signed time beacons (currently fired roughly every 150 milliseconds, with the system clock as the source for now), and block producers select a consensus set of beacons whose median becomes the block time. The second pipeline timestamps user transactions — ideally as close as possible to the moment the user signs — so that transaction ordering is predetermined and the block producer cannot reorder them, eliminating front-running and similar attacks. The team noted current targets are far from the precision they ultimately want, with a two-second tolerance for both drift and spread on the present testnet.

## Verifying Genuine Time Hardware

A core question posed to Timebeat was how the network could verify that a validator is actually running genuine time hardware rather than a plain system clock, since cheating would lower an operator's cost. Timebeat noted that their open time appliances and time cards carry unique MAC addresses tied to the hardware, which could in principle be used as a custom signature and checked against a database. The team raised the concern that, because much network information is public, a validator could claim another operator's MAC address, making this difficult to verify reliably on its own. The discussion turned to what custom signature Timebeat could embed in their hardware that only that hardware could produce.

## PTP² Mesh and Consensus

Timebeat demonstrated their PTP² system, which creates a peer-to-peer mesh that forms a consensus of time rather than a traditional hierarchical tree topology. Key properties highlighted included: the connection to the mesh is fully encrypted (X.509, public/private key), so a node cannot join without keys and cannot inject bad time; a node whose time is deemed incorrect relative to the mesh is demoted to receive-only and cannot distribute time until it realigns; and the system tracks reputation and "root distance" (total error back to a known-good root source), promoting and demoting time sources dynamically while remaining monotonic. Timebeat also described how the mesh scales exponentially across hops, with root nodes (those with genuine GNSS-backed hardware) anchoring the network. The peer-to-peer layer uses libp2p and a distributed hash table was recommended over mDNS.

## Toward Time-Backed Consensus

The discussion converged on the idea that Roko could do more than run its beacon consensus in parallel with Timebeat's timing — it could potentially build a layer of blockchain security on top of the security already provided by Timebeat's time network. Because timing quality scales directly with hardware investment (and cannot be faked by a cheap device running scripts), the network inherently distinguishes meaningful participants, which resembles a proof-of-work signal. The team acknowledged this is a new and hard-to-scope intersection of timing and blockchain expertise, and asked what concepts in Timebeat's world map most closely to a "proof of time." Timebeat suggested that values such as root distance to a known source, reputation score, and active-synchronization status could serve as components of such a proof, while noting that a node's relationship scores are local to the node and cannot be checked remotely without everyone being interconnected — which would not scale.
