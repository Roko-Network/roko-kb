# Development Meeting Summary

**Date:** January 8, 2026

---

## Testnet Credit System

The team reviewed a proposed credit system for the incentivized testnet, designed to track tester involvement so participants can be rewarded later. The system tracks addresses interacting with the testnet, distinguishes regular users from validators, and gathers chain events linked to those addresses. It is built as a modular system: a configuration file defines arbitrary per-address metrics, each pointing to a module that tracks the relevant event, allowing new metrics to be added over time. Known target metrics include the count of temporal transactions per address and, for validators, events about the beacons they fired. The first phase forgoes a database and queries chain history directly (feasible while the chain is small); a second phase would add a simple database for readily available data, which the team felt would make a dedicated credit-system API largely unnecessary. Standard EVM-compatible RPC endpoints and substrate-side filtering already allow historical transaction and address queries.

## Anti-Gaming & Faucet Gating

The team discussed preventing abuse as testing opens to the public. Measures considered include a maximum credit cap per address and gating the faucet so users cannot create unlimited funded accounts. The favored approach gates the faucet behind a social-account link (e.g., a public post), limiting each account to a small daily amount of test tokens — easy to set up and providing both sybil resistance and incidental marketing. Because unfunded private keys are trivial to generate, gating the faucet rather than address creation was deemed sufficient, and transfers from a single funded address to many others remain easily traceable. A community/chat platform integration was also suggested as an interface for related anti-abuse tooling.

## Validator Hardware Attestation

The team explored how to verify that a validator is genuinely running a higher-stratum timing clock rather than spoofing time. Several ideas were raised: asking the timing-hardware vendor whether hardware-level proof of appliance connection is possible; signing a token or message with a secure hardware element to prove a node is backed by trusted hardware; and leveraging the time card's serial number for identification. The team acknowledged it is easier to verify hardware at a point in time than continuously, and noted research into other platforms' hardware-verification approaches, though some of those use proprietary algorithms. Secure-element signing was seen as a promising aid.

## Validator Provisioning Walkthrough

The team did a live walkthrough of the validator provisioning flow, the wallet, and the admin interface. Provisioning generates a mnemonic on the front end, funds and stakes the address with the governance token, tags it as a validator, and provides a script that runs a common binary with the testnet chain spec pre-compiled in (no separate chain-spec file required, though one can be supplied). The team confirmed that building the binary requires per-platform compilation — a Mac build would need to be produced on a Mac, and Linux builds run directly on Ubuntu. They tuned the build to use a bounded number of cores to avoid crashes from excessive RAM use, observing modest memory consumption during compilation. A faucet transaction and a wallet transfer were demonstrated successfully on testnet; the wallet interface mirrors a common browser wallet, and the explorer (currently limited) and chain-events view show propagated transactions. Testnet timestamps currently show zeros because the testnet uses the system clock rather than precision timing.

## Build & Distribution Pipeline

The team agreed to provide pre-built binaries for multiple platforms and to set up CI/CD to produce Docker containers for each component so participants can start nodes quickly. Docker was accepted as the easiest onboarding path, with the team noting it is not a hardware-abstraction layer and runs natively, while leaving bare-metal/individual-OS installs available for performance-sensitive node operators later. A self-hosted runner pipeline that builds for all platforms on tagged releases was discussed to avoid external CI fees.
