# Development Meeting Summary

**Date:** January 27, 2026

---

## Financial Analysis Track

Work is underway on a financial-analysis effort that pulls multi-year datasets (three-to-five-year sets, with a planned move to ten-year sets) from several public data sources and runs Monte Carlo simulations over many iterations with multi-seeding. The intent is to model a range of scenarios over a five-to-ten-year horizon. Results are being kept internal until the underlying data quality is confirmed, to avoid circulating misleading numbers; the team plans to share the scenario list and simulation details to gather feedback on whether the right scenarios and factors are being covered.

## Build Automation

Build automation for Roko Network is in place: when updates are pushed to the main branch, builds for macOS and Linux are produced automatically within about an hour. A separate community-facing bot project, in development for several months, is being prioritized to take advantage of current market attention, with the aim of getting it into users' hands sooner.

## Testnet v3 Branch

A v3 testnet branch is in progress, focused on two areas. The first is re-enabling legacy (non-temporal) transactions in a cleaner way: previously these required a substrate signed extension to mark them as non-temporal, and the detection logic is being rewritten so that genuine legacy transactions (such as a plain transfer) work without that extension. The second is implementing the envisioned temporal transaction system in code. The current v2 testnet remains available and usable via the existing Roko admin interface; the v3 version will replace it once the fee system is added and legacy transactions are fixed.

## Local Testing Environment

To support these refactors, a new local testing setup was built from scratch, since chain spec, parameters, and deployment processes had changed since the previous local environment. The new setup runs three nodes locally, performing both temporal and legacy transactions, deploying the Roko admin interface, and creating validator scripts, bonding, and staking balances. By default it creates a network with three default nodes and then adds two further validators through the Roko admin interface, while checking beacons, health warnings, and errors to enable faster iteration.

## Mempool-Hash Anti-Skipping Mechanism

A previously implemented but untested mechanism to prevent validators from omitting temporal transactions is now being tested. Because the mempool is peer-to-peer and gossiped rather than centralized, an honest validator could build a block missing a transaction simply because it had not yet propagated. The approach splits the mempool into time-framed eras and has validators broadcast a hash of each era alongside their beacons. When producing a block, a validator compares its era hash against the hashes carried by the beacons it must include; a mismatch signals missing data, and the validator requests the missing transactions from a peer with a different hash, updates its mempool, and re-checks until the hashes align. The overhead on gossiping is minimal (one additional hash per beacon), but the potential slowdown to block production — since a producer may need several rounds of requests to reconcile — still needs to be measured. The improved local testing environment now allows many such scenarios, written with the help of agents, to be run overnight.

## Time-Security Research

In parallel, a research effort was set up using agents to collect and explore documentation, articles, and links from the recent timing-partner discussion, with the specific goal of finding a way to use the security of the time-protocol networks as a consensus mechanism for the chain itself. This work is being monitored but is not displacing the coding tasks.
