# ROKO Temporal Discussion

**Date:** March 24, 2026

---

## Deadline System Validation

The infrastructure lead reported on the simpler deadline-based design that replaced the court system. Rather than spending days reconstructing rare failure scenarios, the team ran the full regression suite for five days, firing many transaction types with different delays across different nodes — including a deliberately disruptive node ("Charlie") that delays, fails to respond, and syncs improperly by design. After five days of varied usage with five simulated users and full rejection-path testing, the results matched expectations: no regressions, the small percentage of transactions that previously suffered significant delays from court syncing no longer did so, and zero transactions were rejected, despite the new system retaining an extremely small theoretical chance of rejection. The team considers the issue effectively resolved while acknowledging it is very hard to simulate.

## A Proper Block Explorer

The main work item discussed was building a complete block explorer. Current monitoring relies on a working wallet, an admin dashboard for creating validators and monitoring the chain, and a lightly modified Polkadot.js-based explorer that lacks a database and cannot search transactions. The plan is to fork BlockScout — the most feature-complete open-source explorer — and rewire it to the network with AI assistance, since the open-source codebase has abundant examples and progress is easy to verify by checking whether features work. The lead estimated a fully operational explorer could be achievable within a week, which would also reduce ongoing maintenance burden compared with maintaining both a custom Polkadot.js explorer and a separate BlockScout deployment.

A nuance discussed: BlockScout is designed for EVM chains and is blind to substrate-specific interactions, while the network is fundamentally a substrate chain offering far more than EVM. Although precompiles expose staking, unstaking, power, and balance operations to both smart contracts and explorers, substrate-level access remains important because that is where core activity originates. The team noted that the testnets were reset to support rebuilding a custom BlockScout version, since signatures and signing changed substantially after the time RPC was removed in favor of standard signatures via the temporal mesh.

## Agentic-First Tooling and APIs

The team agreed that the primary consumer of explorer and chain data will be agents rather than humans, and that an agentic entry point should be prioritized. This was framed less as needing a dedicated MCP server and more as enriching APIs, shoring up Swagger specifications, and providing clear examples and documentation, since agents need extra explicit help. The wallet's accessibility was also discussed; with validators now timestamping transactions themselves, the rationale for a fully custom wallet is reduced, and standard substrate wallets and MetaMask are already compatible. The team noted that a custom data wallet remains in the broader roadmap as part of the wider data-architecture effort.

## Data Architecture and Secure App Pattern

A second update covered the team's data-architecture and graph system for AI, described as a "data wallet" intended to run on the network. A companion browser-based component was demonstrated that runs roughly seventy percent of the full system inside the browser, enabling a Proton-style architecture: user data is encrypted on servers and a thick client downloads and unpacks sharded encrypted files locally, keeping servers simpler and the system highly secure. The demonstration showed multiple applications sharing a single data system through app tenancy, with data organized by full-text search, flat tags, and a hierarchical tagging scheme, plus the concept of embedding sets — search filters applied to data to produce scoped embeddings for production use. The discussion explored the trade-off between heavily structured tagging (useful for tightly bound domains such as game data) and a rawer embedding approach that avoids over-constraining what can be retrieved. A research paper on classification and avoiding tool-domain traps was referenced as relevant to this filtering logic.

## Integration Roadmap and Killer-App Discussion

The team agreed to hold a dedicated session to walk through each member's work — the data system, the agent tooling, and the white-label plans — and to integrate roadmaps more tightly by actively using each other's libraries. A possible addition to that conversation was a separate intent-based DeFi execution engine in which the network holds a stake: it exposes a CLI and MCP, lets agents interact with DeFi through intents rather than raw smart-contract calls, and includes a wallet that allows agents to act without exposing private keys via automatic external cosigning. The team reiterated that a decentralized-exchange "killer app" is not yet viable due to liquidity requirements, so a value-creating application that does not depend on deep liquidity should be identified instead.

## Distribution Strategy

The team discussed packaging an agent-first, well-documented NPM package, branded for the project, as a distribution mechanism — making it an easy dependency that handles wallet creation and payment authorization automatically on install, so that agent-driven developers adopt it without friction. Connectivity issues with the meeting platform were noted throughout, prompting discussion of more stable alternatives, including a self-hosted option.

## Other Updates

A separate experimental effort was described integrating a vectorized short-term memory system for agents — fact and entity extraction stored into the data system, dynamic context injection, and automatic compaction summarizing key points every few turns — with a goal of demonstrating long-term-memory conversation. A pending sales-call opportunity was noted as a potential real, end-to-end use case spanning front end, the DeFi engine, the data system, and the network.
