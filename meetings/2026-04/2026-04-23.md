# Development Meeting Summary

**Date:** April 23, 2026

---

## Timing Hardware Validation

The protocol engineer reported extensive hands-on work bringing up a validator on a Timebeat-class timing device shared by the team, accessed remotely over Tailscale. The board was able to join the mesh and produced an initial batch of blocks, but was repeatedly ejected from mesh consensus due to time drift and packets failing to reach other nodes quickly enough. After roughly twenty-one hours across two days — rebuilding node versions, relaxing networking acceptance criteria, and trying several timekeeping configurations — the current assessment is that the difficulty is primarily a configuration issue rather than a device limitation, though Chrony was observed to keep better time than the device itself, which is not the desired outcome. The board lacks an onboard oscillator with strong holdover, a likely contributor to the drift. A higher-tier precision board with an onboard oscillator is expected to be available for testing within roughly one to two weeks, allowing two nodes on the same LAN.

The team also noted that a poorly configured device can, given the small validator set, break the chain's timekeeping and place it in a semi-unrecoverable state requiring an admin refresh function — underscoring the value of this real-hardware testing in finding the threshold between an acceptable contribution and one harmful to the network. The next milestone is sending transactions to the node for timestamping to observe raw time data from the hardware for the first time.

## Networking and Latency

The team discussed reducing validator latency, noting the current setup routes traffic through a VPS acting as an exit node over a mobile VPN path, which is not ideal for the timing-sensitive validators. Options weighed included port-forwarding the device through the operator's own router with a local proxy versus standing up a lighter-latency VPS closer to the other nodes. For exposing the node, the consensus was that straightforward port forwarding of the gossip-channel port is sufficient for now, with acceptance criteria able to be tightened again as the network grows.

## Hardware-Authenticated Timing Concept

A team member presented an executive summary of a proposed mechanism to detect and authenticate the timing hardware a validator is actually using, based on the characteristic phase-noise signature of different oscillator classes. The concept is explicitly additive and not a replacement for the existing Grandpa/Babe consensus; it is intended to let peers observe whether a neighbor's phase noise is honest and to make hardware-level timestamping harder to spoof in software. The proposed rollout proceeds through tiered roles — a monitoring observer role first, then an advisory role, and only later a production-gating role — with a built-in safe-valve that falls back to advisory mode if a large fraction of nodes appear to be misclassifying their clocks, so the mechanism cannot itself destroy the mesh.

The team agreed to begin by integrating the approach at the monitoring level, provided it does not meaningfully increase compute load, log volume, or node latency, observing what it reports as participants join the testnet. If it proves reliable over a few months, it could later gate validator capabilities — for example, allowing a node to produce blocks but not to timestamp if its time source is insufficient — and underpin economic incentives. It was emphasized that the underlying verification math should be designed to be interchangeable so alternative approaches (such as different noise or integer-series methods) can be swapped in. Running the concept as a pilot was preferred for manageability.

## Next Steps

- Continue tuning the timing-device configuration and networking to achieve reliable block production, then send timestamping transactions to observe raw hardware time data.
- Stand up the higher-tier precision board as a second node on the same LAN for comparison.
- Reduce validator latency by improving the network path (port forwarding with a local proxy, or a lighter-latency VPS).
- Integrate the hardware-authentication mechanism at the monitoring level as a pilot, validating its resource footprint before any gating role.
