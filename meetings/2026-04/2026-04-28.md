# Development Meeting Summary

**Date:** April 28, 2026

---

## Fortemi Wallet and Hall of the Mind UI

The team reported that tooling developed on a partner red-teaming project is being normalized and consolidated into products, some of which will be open source or free to use and some packaged for enterprise customers. A pattern from that work — a browser-based agent able to control multiple applications with embedded memory, runnable without installing an application — is expected to become an entry point for trying Fortemi and related tools. As a direct result of that cross-project work, Fortemi can now ship as regular downloadable Linux and macOS application installers.

Hall of the Mind (HRTM) was confirmed as the front-end UI for Fortemi, now public in its repository with DMG, DEB, and RPM release packages. Installing the front end automatically stands up Fortemi and Postgres in the background, lowering the setup burden compared with the prior Docker-based flow. The application is built with Rust and Tauri wrapping a React app, and can also still run as a Docker module pointed at an existing Fortemi server. The current build is a developer package without a full Apple signature, so it requires allowing developer packages; the team considers it close to, but not yet ready for, general advertisement until the Apple signing is set up properly. Hall of the Mind was noted as the original prototype Fortemi grew out of before the server was separated from the UI.

## Timing Hardware Progress

The protocol engineer reported the timing device's clock was stabilized using a hybrid setup combining Chrony with the time card, but that the card drifts significantly on its own, pointing to a weakness in this particular hardware. The conclusion is that the board can serve as a smaller node — still producing blocks and earning some weight for lower-tier timestamping — but will not reach the time quality needed for the full timestamping rewards. The team discussed the underlying cause: the board lacks an onboard quartz oscillator and therefore has little holdover, so although it can report nanosecond accuracy it can drift onto the wrong UTC second. A driver issue was also raised as a possible contributor.

The discussion reinforced the network's core design intent: an individual node with weaker hardware can still participate because what ultimately matters is that the mesh agrees on the time, with the chain computing a time-quality number per validator and one for the mesh as a whole, enabling and disabling features as quality changes. The team noted that running multiple coordinated reference clocks (ideally three) is part of how the hardware stays in sync, and expects that once enough high-quality reference nodes and proper grandmaster setups are running, edge participants will need progressively less intensive hardware. Plans include exposing a grandmaster node so other operators can synchronize against it, and adjusting the time-quality formulas so that operators who invest in strong hardware are appropriately rewarded. A full pass on the reward system surfaced and resolved one imbalance, prompting a node rebuild.

## Reward Token Open Questions

The team revisited whether timestamping and other rewards should be paid in the native coin or in Power Roko, the staking-oriented token. The distinction matters because Power Roko was conceived as a staking instrument with specific legal properties (including a two-week unlock and tax-simplification intent), and paying general rewards in it could undermine those properties and add ecosystem complexity. The protocol engineer flagged this as a tokenomics rather than a technical decision and declined to assume the answer, keeping non-staking reward paths in the native coin pending direction. The team noted general appreciation for the locking mechanism as a way to control liquidity and, potentially, to let holders manage when they realize value.

## Token Structure and Ethereum Token

A continued discussion explored separating governance and utility roles across the existing Ethereum-based token, the native chain coin, and Power Roko, with broad agreement to re-roll the Ethereum token so it no longer needs to be part of the chain's economics or governance. One direction discussed treats the existing token as a representation of the secured core of the network — potentially free to appreciate in price — while keeping the chain's operational token stable and inexpensive so that services priced in it remain predictable for enterprise customers. The team noted the current holder distribution appears reasonably fair per third-party analytics, and weighed the risk that long-dormant holders may not actively use the network. Migration mechanics (a claim contract and bridge, an exchange ratio or decimal pre-inflation, and a token burn) were discussed at a high level as options to be detailed later. The team agreed to consolidate the tokenomics options into a shared document for structured comparison and broader input.

## Business and Operations

A brief operational note covered an ongoing external services discussion that has been on hold; the team agreed to re-engage the counterparty directly and reset expectations, emphasizing that committing to significant recurring cost is premature until the network can demonstrably generate revenue. No private figures or counterparty negotiating details were resolved in the meeting.
